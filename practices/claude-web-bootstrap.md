## Rule
Every project set up with Precedent for me to work on from Claude Code Web gets a `SessionStart` hook that clones or updates `precedent-individual` and writes `~/.config/precedent/config.json`, before the session's first tool call. I never run a command myself for this -- not to clone the repo, not to write the config -- so the individual source is already resolvable the moment work starts.

## Detail
The hook is synchronous, not async, on purpose: an early tool call resolving practices before the individual source exists would silently degrade (correctly, per the resolver's own contract -- but not what should happen every single session). Synchronous removes that case outright -- see the Story below for the different, harder case it does NOT remove, and why a retry loop inside this hook cannot remove it either (corrected 2026-09-06; an earlier version of this Detail claimed the opposite).

**A retry loop inside this hook cannot close the `add_repo` access gap, at any attempt count or delay -- confirmed by direct test, not just argued.** This hook needs the session to already have git read access to this private repo, and that access is granted per session by the agent's own `add_repo` tool call, in the agent's own turn. A `SessionStart` hook runs *entirely to completion* before that turn starts (Claude Code's own docs for this hook: synchronous mode "guarantees dependencies are installed before your session starts") -- a strict ordering, not a race with variable odds. So on a genuinely fresh session, every attempt this hook could make, at any retry count, runs before `add_repo` can have fired even once; there is no point during this hook's own execution where that access could appear. **What actually closes the gap**: BestPractice's own `tools/precedent_resolve.py` re-invokes whatever hook a project installed from this file, lazily, the first time anything performs a live resolve and finds the config still absent -- and because that re-invocation happens from inside the agent's own turn, always after `add_repo` has already run, this hook's own single attempt succeeds there, normally.

It fails gracefully rather than failing the session: if this environment can't reach `precedent-individual` (no credential, no network), the hook says so on stderr and exits 0 -- team and universal still resolve, and the missing-source message is the same one `precedent_resolve.py` already prints for any absent source, not a special case.

This is a per-project install step, not a one-time global setting -- `SessionStart` hooks live in a project's own `.claude/settings.json`, so each project that wants this needs the hook installed once, the same way it needs Precedent's `precedent.json` installed once. See `precedent-team-maintainers/practices/install.md` for where this step belongs in that procedure. The actual script content must be **copied** into the target project's own `.claude/hooks/`, not referenced by a path under `$HOME` -- on a brand-new container nothing under `$HOME` exists yet, so the hook that creates `$HOME/precedent-individual` can't itself live inside it.

## Why
Most of what a personal preference layer like this ever needs from me is nothing at all -- and for anyone this pattern serves who isn't a developer, "clone a repo and write a config file" was never a reasonable one-time cost, let alone a per-project one. The friction was a bootstrapping gap in an otherwise sound design (a separate private repo, never vendored into a shared project), not a reason to weaken the privacy separation itself.

## Story
Raised directly in a conversation where testing this against a fresh repo turned out to be blocked by this session's own repo scoping -- which is what surfaced that a session-level "add a repo" capability isn't actually wired up in this environment, separately from the bootstrap question itself.

**v2, 2026-09-05: two independent projects that had installed v1 of this hook hit the identical failure within about a day of each other.** Each had also followed the standing instruction this practice's own Install section (and BestPractice's `spec/MIGRATING_EXISTING_INSTALLS.md`) called for: tell the agent to call `add_repo` for the individual repo "before running any bootstrap script." In both cases the hook ran, found it had no read access yet, degraded on purpose -- correctly -- and then never ran again. One session noticed only because a later command failed with "unknown slug" and traced it back by hand; the other noticed only because a stale freshness check looked clean with the individual source silently absent, indistinguishable from "this person genuinely has no individual set." Neither installation was wrong by this practice's own stated rules -- the rules themselves assumed a `SessionStart` hook and an agent's own first tool call could be ordered by instruction alone, and it took two incidents to show that false: an instruction cannot make a tool call precede a hook the harness already started running. Fixed by giving the hook a bounded retry (this file) and, on the BestPractice side, a lazy self-heal in `tools/precedent_resolve.py` -- see BestPractice's `practices/session-bootstrap.md` Story for the fuller incident record and `tools/precedent_source_bootstrap.py` for the equivalent, Python-based mechanism BestPractice's own installer template now ships.

**v3, 2026-09-06: half of v2's own fix was wrong, found the very next day.** v2's retry was verified only by calling it directly and checking it retried the stated number of times -- never inside a real `SessionStart` hook on a genuinely fresh Claude Code Web session, which is the one environment where the claim actually mattered. A follow-up testing session ran that real test, twice, in `HavrutaBrainstorm`, and confirmed directly: a `SessionStart` hook's execution window and the agent's own first turn never overlap in time, so retrying inside the hook is not a partial mitigation of the `add_repo` gap, it is inert for it -- v2's header comment claiming synchronous-plus-retry "closes the common case" was simply false, and it had been quietly costing every cold session up to ~12 seconds of latency for that zero benefit. The lazy self-heal half of v2's fix was unaffected and re-confirmed to work, because it runs from inside the agent's own turn, after `add_repo`, which is the one point in the sequence where the access actually exists. Fixed by defaulting this hook back to a single attempt (retry stays available as a plain script constant, opt-in, for an unrelated genuine transient-network case -- never claimed as a fix for this one) and correcting every place, including this file, that had credited the retry as a real, contributing half of v2's fix. Corrected the same day in BestPractice too ([`tools/precedent_source_bootstrap.py`](https://github.com/alex137/BestPractice/blob/precedent-beta-v01/tools/precedent_source_bootstrap.py), [`practices/session-bootstrap.md`](https://github.com/alex137/BestPractice/blob/precedent-beta-v01/practices/session-bootstrap.md)).

## Install
The canonical script and settings snippet live in this repo, at `bootstrap/session-start.sh` and `bootstrap/settings.snippet.json`. Installing into a project:

1. Copy `bootstrap/session-start.sh`'s content into the target project as `.claude/hooks/precedent-individual-bootstrap.sh` (executable).
2. Merge `bootstrap/settings.snippet.json`'s `hooks.SessionStart` entry into the project's own `.claude/settings.json` (create it if missing; append to an existing `SessionStart` array rather than replacing it).
3. Commit both as tracked files in the project -- this only works because they're present the instant the container starts, before anything else runs.

Validated end-to-end 2026-08-31: a fresh clone, an idempotent re-run (pull path), and the non-remote no-op all behaved as described, and `precedent_resolve.py` picked up the individual source afterward with no other setup. Re-validated 2026-09-05 for v2 (the retry): an unreachable repo URL retries the stated number of times then degrades exactly as v1 did, and a reachable one still clones/pulls and writes the config identically to v1 -- the retry changes nothing about the success path. Re-validated 2026-09-06 for v3 (the correction): with the default back to one attempt, an unreachable repo URL now degrades in well under a second rather than v2's ~12-second exhaustion, and the success path is still byte-identical to v1/v2 -- see Story for why the retry itself never affected the success path either way.

Checked mechanically by [`tools/checks/check_claude_web_bootstrap.py`](../tools/checks/check_claude_web_bootstrap.py), scope `tree`, with a deliberate limit: the practice's actual claim -- "every project gets this hook installed" -- is about *other* projects' `.claude/` trees, which a check living in this repo can't see. What it verifies instead is that the two canonical artifacts this repo publishes for other projects to copy still hold the structural invariants this file's own Detail section requires: `bootstrap/session-start.sh` is git-tracked executable and never exits non-zero (fail-gracefully, not fail-the-session), and `bootstrap/settings.snippet.json` is valid JSON whose hook command doesn't reference `$HOME` and whose hook entry isn't marked `"async": true`. If either file regresses on any of those, every project that copied it breaks the same way. Two-direction tested in [`tools/checks/tests/test_claude_web_bootstrap.sh`](../tools/checks/tests/test_claude_web_bootstrap.sh), one planted violation per invariant.
